# V3.1 连续衔接时间轴

## 问题与修改范围

V3 用全局进度打开/收拢格阵，但每块格片又有自己的出发/抵达时刻。在五次缓入缓出曲线的端部，位置变化很小；部分格片还会已经拆开而尚未出发，或已经停止而尚未填缝。手动拖动也能复现，因此不能只把它归咎于帧率。

本修复不改变颜色配对、采样、映射算法、贝塞尔控制点或默认 5.8 秒总时长。`src/matcher.js` 和 `src/transport.js` 与 V3 源文件逐字节相同。五组默认图片的映射哈希保持不变。

## 共享局部进度

`src/timing.js` 是时间设计的唯一来源，同时生成 JavaScript 与 GLSL。设总进度为 p，每片由原有颜色相关属性映射得到出发 s 和抵达 e：

```text
s ∈ [0.015, 0.050]
e ∈ [0.950, 0.985]
u = clamp((p - s) / (e - s), 0, 1)
```

该压缩保留原有颜色相关出发次序；不是把所有格片设为同一开始时刻。

## 位移进度

设 r = 0.08。开头采用余弦速度的积分：

```text
edge(u) = [u - r/π · sin(πu/r)] / [2(1-r)]
T(u) = edge(u)                          u < r
       (u - r/2)/(1-r)                 r ≤ u ≤ 1-r
       1 - edge(1-u)                   u > 1-r
```

这在端点以零速度起止，短距离内完成加减速；中间保持恒定的**曲线参数速度**。它不是弧长参数化，因此不能宣称所有格片的屏幕像素速度恒定。轨迹仍为原来的三次贝塞尔曲线。

## 格阵与填缝

设 S 为 clamp 后的三次 smoothstep：

```text
M(u) = S(u/0.10) × [1 - S((u-0.88)/0.12)]
```

局部进度刚开始时已经有位置变化，同时逐渐打开格片缝隙。局部进度 88% 后开始填缝，在每块格片自己的抵达时刻同时结束。背景底色包络独立存在，不参与决定格片的行程结束。

## 实测与边界

`reports/handoff/report.json` 记录五组实际素材的检查，包括映射哈希一致、旧停顿区的运动采样、真实 WebGL 像素差异、完整画面循环接缝。样本窗口覆盖出发衔接与抵达衔接；测量的是选定窗口中有非零路程格片的参数运动，不应把计数解读为“掉了多少帧”。

`tests/test_timing.cjs` 还检查有限数值、端点、单调性、短加减速段接缝、4/5.8/8 秒时间抽样及参数校验。浏览器测试在软件渲染环境中执行，不等同于用户硬件的帧率基准。

完整原图之间的 3.2 秒停留仍然是主动设计，可通过 `options.holdTime` 调整。首次建立映射、改变尺寸后重算、没有 Worker 时的计算等待属于另一类问题，没有用本补丁伪装为已经消除。
